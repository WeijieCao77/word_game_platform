## 怎么回滚（一步，不用进 Railway 控制台）

跑 `Build and deploy` 这条 workflow，**把 ref 选成要退回的那条 rollback 分支**：

- 网页上：Actions → Build and deploy → Run workflow → Use workflow from → 选
  `rollback/v20260826-3` → Run workflow
- 或者让 AI 用 GitHub 工具 `run_workflow`，`ref` 填那条分支名

三五分钟后线上就是那个版本。核对方法是 `GET /api/health` 看 `build.commit`
是不是那个 commit 的前 7 位。

### 为什么这样行得通

部署工作流里有一道「我是不是已经过期了」的守卫，它比的是
**这次 run 的 commit** 和 **`$GITHUB_REF_NAME` 这条 ref 的最新 commit**。
从 rollback 分支跑时两者天然相等，所以守卫放行；
而从主分支跑的旧 run 会被它拦下——两种情况都是我们要的。

已经实跑验证过一次（2026-08-26，dispatch `rollback/v20260826-3`）。

## ⚠ 回滚之前先按住自愈守卫

仓库里有一条 `线上版本自愈守卫`（`.github/workflows/deploy-guard.yml`），
每 20 分钟对一次「线上跑的 commit」和「分支最新的 commit」，对不上就自动把线上顶回最新版本。
它治的是「旧的部署 run 半夜醒过来，把线上悄悄退回去而没人知道」——今天真差点踩到。

**它不知道你是在故意回滚。** 所以按刹车之前先建一条空分支把它按住：

```bash
git push origin <当前线上那个 commit>:refs/heads/rollback/HOLD
```

守卫看到 `rollback/HOLD` 存在就完全不动手。修好之后把它删掉：

```bash
git push origin --delete rollback/HOLD
```

忘了删的话，守卫会一直不管事——那正是「线上悄悄退回去」这类事故的温床。

## 回滚之后要做什么

回滚只是**急刹车**，不是修复。主分支上那些代码还在，下一次推送会重新把新版本带上线。
所以刹完车之后必须二选一：

1. 把有问题的改动用 `git revert` 从主分支撤掉，再正常部署；或者
2. 把问题修好再部署。

不要靠「一直不推送」来维持回滚状态——下一个人一推就破功了。
