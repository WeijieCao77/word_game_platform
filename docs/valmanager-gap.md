# 硬碰硬：我做的那两款，离 VAL MANAGER 到底差多远

老板的原话是「纯属垃圾，和原本的 val manager 压根不相干」。他是对的。
这份文档不辩解，只把差距逐项摆出来，并说清楚**为什么**差成这样、**要补什么**才能真的 1:1。

---

## 一、并排看

| 维度 | 原版 VAL MANAGER | 我做的 `vct-manager` / `kpl-manager` |
| --- | --- | --- |
| **时间粒度** | **按天**推进，一年 336 天，赛季内分 11 个赛段（季前/kickoff/Masters/Stage/Champions/休赛期…） | 每周一次，一季 13 周，没有赛段 |
| **一天做什么** | 12 类具体事务，各有独立界面：提交报价 / 答复报价 / 挂牌 / 解约 / 商务活动 / 拜访赞助商 / 筹备俱乐部活动 / 直播合同 / 约训练赛 / 教练组 / 设施升级 | 3 个行动点，从 15 条决策里点几下 |
| **比赛** | BO1/BO3/BO5；**地图 ban/pick 流程**；**逐回合模拟**，一回合 420ms 跑给你看；中途有**两次战术暂停**可以改战术滑条；跳过则同一套模拟直接跑完 | 一次结算，直接给一个比分和一段话 |
| **比赛解释** | `EdgeBreakdown` 逐项拆解优势来自哪里；`RoundRibbon` 把每一回合画成条带 | 结算中间量面板 |
| **训练** | 每人每周专项 + 队伍集训（TeamDrill）+ **双人搭档**；**计划确认后锁定一周**，中途改要付一周代价 | 点一次「专项特训」，选一个人，立刻生效 |
| **阵容** | **按地图选阵容**，角色适配度影响发挥 | 主力/替补标签 |
| **转会** | 多维报价评分（价钱/角色承诺/出场时间/球队实力/球员意愿）；球员会拒绝；**AI 球队之间自己也在转会**；别人会来买你的人并等你答复 | 报价 → 等 2~4 周 → 按概率成或不成 |
| **员工** | 主教练/助教/分析师三档，分析师 5 种专精（地图/对手/潜力/经济/复盘）；**去挖别队的教练**；设施等级升级 | 一个主教练，三个属性 |
| **数据** | 每人 10 项赛季统计（场次/回合/击杀/死亡/助攻/首杀/首死/伤害/残局/MVP），赛后入账 | 无 |
| **关系** | 两两羁绊 + 队内和谐度 + 每人对你的信任，坐板凳会掉、队友离队会连带 | 队内默契（有了，但只有一层） |
| **生涯** | **没有结局**。被解雇是「任期结束」，可以去应聘别的俱乐部继续；年份一直往前 | 三个赛季，8 个结局 |
| **界面** | **26 个专属界面**，共 5,839 行：训练室、转会市场、商务、阵容、赛程、积分榜、对阵表、财务、生涯、教练组、球员详情、赛前布置、逐回合直播… | 通用播放器的 5 个页签，所有游戏长得一模一样 |
| **世界规模** | 78 支战队 / 518 名选手（真实 VCT 数据） | 10 支对手 / 18 个实体 |
| **代码量** | 引擎 7,010 行 + 界面 5,839 行 | 一份 JSON 配置 |

## 二、为什么差这么远——三个真实原因

### 1. 我把「用平台的积木拼一个电竞经理题材的游戏」当成了「复刻」

这是我的错，而且是判断上的错，不是执行上的错。我做出来的东西，**共享的只是题材词**：
都叫电竞经理，都有选手和赛季。但玩家坐下来玩的那个东西是两个游戏。
我还用了「同体量」这个说法——不该用，那是在给差距找台阶。

### 2. 平台引擎的表达模型撑不住这种玩法

平台的模型是 **「回合 → 抽卡/决策 → 结算 → 出结果」**。它能表达
「一次判定，给一个结果」，表达不了：

- **过程本身是内容**的场面：逐回合的比赛、可以中途叫暂停改战术
- **多阶段的一场对局**：ban/pick → 选图 → 打三张图 → 每张图 13 回合
- **计划与承诺**：这周定了的训练计划不能反悔
- **世界自己在动**：你不操作时，别的队也在转会、也在变强

这些不是「配置写得不够多」，是模型的表达力上限。

### 3. UI 是硬伤，而且是**平台化的固有代价**

原作有 26 个为这个题材手写的界面。平台只有一套通用播放器——
**只要平台只有一套通用 UI，任何游戏都不可能长得像 VAL MANAGER。**
这一条靠加配置字段解决不了，得改平台的界面架构。

## 三、要真的 1:1，平台必须补什么

按「补上之后离 1:1 还差多少」排序：

| # | 能力 | 为什么它是卡点 | 量级 |
| --- | --- | --- | --- |
| 1 | **界面 schema**：让作者/AI 定义面板长什么样、放哪些块、怎么排 | 不做这个，所有游戏永远长一个样 | 大 |
| 2 | **分步可介入结算**：一场对局分成若干步，玩家可以中途改策略；支持多局制与赛前博弈（ban/pick） | 逐回合比赛、庭审、谈判、直播带货全靠它 | 大 |
| 3 | **按天推进 + 赛段**：时间的第三级结构，以及「今天能做几件事」的日程模型 | 现在只有 回合/周期 两级 | 中 |
| 4 | **世界自主演化**：你不操作时对手也在转会、成长、换教练 | 已补一个原语（曲线的 `pick: "one"`），但联赛队伍强度仍是死的 | 中 |
| 5 | **周计划锁定**：定了就要执行完，改要付代价 | 让决策有承诺成本 | 小 |
| 6 | **生涯迁移**：一段任期结束后换东家继续，状态部分继承 | 原作根本没有结局 | 中 |
| 7 | **实体统计累积**：每人每赛季的 KDA 之类，能聚合能展示 | 现在实体只有静态属性 | 小 |
| 8 | **资源与数据文件**：518 人的真实数据不该塞进 JSON 配置 | 见下 | 中 |

## 四、老板提的那条是对的：游戏不必只是一份 JSON

> 「做游戏不是一定只能做成纯粹的 json 文件，我们后台也可以存储文件，
> 平台也可以提供存储空间。」

这条直接指向第 1、8 两个卡点。三种走法，从轻到重：

**A. 数据文件（轻，该马上做）**
配置里只写规则，**数据放独立文件**：518 名选手、78 支战队、赛程表，
以 CSV/JSON 数据集的形式存在平台的存储里，配置通过引用取用。
好处：配置不再撑爆上下文；作者可以直接上传自己的数据表（真实赛事数据、
自制角色表）；AI 也不必逐条生成几百个实体。

**B. 界面 schema（中，这是「长得不一样」的根本解法）**
不是让每个游戏自带前端代码，而是让平台提供一套**界面积木**
（面板、表格、分栏、卡片、进度条、对阵图、时间轴…），
由配置描述「这个游戏的主界面由哪些块组成、每块显示什么」。
这样《修仙人生》和《电竞经理》可以长得完全不同，而平台仍然只维护一套渲染器。

**C. 受限脚本（重，暂不做）**
让游戏携带自己的代码。表达力最强，但安全、审核、维护成本都是数量级上升，
而且违背「创作者只靠对话就能做游戏」这条产品前提。交接文档里当初把
「沙箱脚本层」列为暂不做，这个判断现在依然成立。

**结论**：走 A + B。A 先做（马上能让数据规模上一个台阶），B 是接下来最大的一块工程，
也是唯一能让「不同游戏长得不一样」的路。

## 四点五、自由模式落地之后，这张表要重画

（2026-08-25 晚补记。老板重申：**验收标准就是用平台一模一样做出 VAL MANAGER 的完整版**。）

第三节里排第 1 的卡点是「界面 schema」，当时判断要做一套界面积木。
后来老板给了更彻底的方向——**平台是工作台，游戏长什么样是作者自己的事**，
于是走了「自由模式」：作品自带一套网页文件，跑在沙箱 iframe 里，
界面与玩法结构全部由 AI 写的代码决定。这一条落地之后，上表要重排：

| # | 能力 | 自由模式之后 |
| --- | --- | --- |
| 1 | 界面 | **不再是平台的卡点**——26 个专属界面就是 26 段 HTML/CSS/JS，写就完事 |
| 2 | 分步可介入结算 | 同上，逐回合比赛、战术暂停都在作者自己的 js 里 |
| 3 | 按天推进 + 赛段 | 同上 |
| 6 | 生涯迁移 | 同上 |
| 7 | 实体统计累积 | 同上 |
| 8 | 数据文件 | 仍要做：518 人的名单不该硬编在 js 里，该是平台存储里的数据文件 |

也就是说，**自由模式把「平台表达不出来」这件事基本解掉了**，剩下的卡点换了一批，
全是工程性的：

1. **一轮请求做不完一个大作品**。线上实测反复撞 502 Application failed to respond。

   **关于 502 的原因，我先给了一个结论，后来发现证据不够，这里更正**：
   我一开始判定是「模拟把事件循环占死」——这条测量本身是实的
   （kpl-manager 600 局要 30 秒纯 CPU，那段时间服务对外确实没反应），
   但把它当成 502 的**唯一原因**是过头了：第三次实测里，**第 1 轮**
   （纯聊方案、不跑模拟、不动工具）同样连撞三次 502。
   更符合全部现象的解释是：我当晚在密集推送，**每次推送都触发 Railway 重新部署、
   容器重启**，而三次实测的窗口每次都压在推送上。

   两条都已经动过手（模拟限流到 150 局 + 单轮 40 秒墙钟预算 + 改一次存一次），
   这些改动本身该做；但「502 到底是不是我自己推挂的」还需要一次**推送静默期内的
   干净实测**才能定论。做这个判断时别再只看一次运行就下结论。
2. **AI 一轮能写多少代码**：单文件上限 40 万字符不是问题，模型一次输出的量才是。
   VAL MANAGER 是 13,132 行——必须能分文件、分轮次地写，而且第二轮要读得懂第一轮写的。
3. **自由模式没有护栏**：三级校验与 600 局模拟是给通用引擎用的，
   自由模式只剩几条机检（有没有入口、有没有碰沙箱禁区、存档桥接没接）。
   一个 13,000 行的游戏是不是真能从头玩到尾，目前没有自动的答案。

**下一步该验的，是第 1 条**：让线上的 AI 分多轮把一个作品搭到几千行，
中间不掉链子。这条通了，「一模一样」才从「表达得出」变成「真做得出来」。

### 第 9 次实测（2026-08-26，run 32928990941）：绿的，但绿得不好看

这一次带了「等部署跟上」的 gate，是第一次干净的实测。结论分两半：

**做得出东西了**。AI 写出 index.html 23,749 字符，冒烟检查五项全过——
打得开、有得点、点得动、手机不溢出。第 8 次那个红（「点了几下内容都没变化」）
是**检查器的问题不是作品的问题**：它定死等 2.5 秒就下结论，而文字游戏开场是
打字机一句句往外冒。改成「等文字不再变化再判断」之后，同一条线上通路就过了。
（放宽有没有变成摆设？专门验过：故意做一个「按钮绑了空事件」的样例照样判红。）

**但账很难看**，四条都要记下来：

1. **额度：6 轮烧掉 410,754 token，超了游客一天的 400,000 上限。**
   老板问过「自由模式的 token 消耗是否会飞速增长」——这就是答案：会，而且一次坐下
   就能把一天的额度用光。逐轮是 18k → 53k → 185k → 219k → 280k → 410k。
2. **6 轮里有 3 轮只交出了「这一轮做到这里先交个底」**（第 2、4、5 轮，
   分别耗时 290s / 204s / 265s）。墙钟预算保住了「不卡死、已做的存下来」，
   但对创作者来说那三轮的体感就是「等了五分钟，什么都没发生」。
3. **两轮的工具调用被当成正文吐了出来**（第 3、6 轮）：模型没走结构化的
   tool_calls，而是把 `<｜｜DSML｜｜invoke name="update_config">…` 打进了回复里。
   于是工具没执行、配置一个字没落——AI 想改的标题「星澜电竞经理」最后压根不在配置里，
   而这两轮的 token 照收。**已修**（src/lib/ai/inline-tools.ts：从正文里把调用捞回来
   当真调用执行，标记从正文抹掉）。
4. **仍然是单文件**：23,749 字符全塞在 index.html 里，没拆 style.css/game.js，
   也看不出用过 patch_file。技能包里的「分轮搭建纪律」写了，但没被照做。
   VAL MANAGER 是 13,132 行——照这个写法，第二轮想改一处就要把两万多字符重吐一遍。

也就是说，「能做出一个能玩的东西」这一步过了；「能一层层搭到几千行」还没过，
挡在前面的是**每轮的产出效率**，不是平台的表达力。运行库（wgp.js）和数据表
就是冲着这一条去的：把每部作品都要重写的那部分（存档桥、界面路由、表格、打字机）
和数据（几百个实体）从模型的输出里拿走，AI 那一轮才有余力写真正属于这部作品的东西。
下一次实测要盯的三个数：**每轮 token、拆了几个文件、patch_file 用没用上**。

## 五、这两款怎么处置

已从游戏库撤下（`seedDemos` 里删掉了）。它们本身能跑、也过得了所有门槛，
但**挂在官方示例里冒充 VAL MANAGER 复刻是有害的**。
等平台补上第 1、2、3 项能力之后再重做——那时候才配叫复刻。
