# 网页文字游戏创作平台 —— 项目交接文档

> 项目起点文档，保留原文备查。后续讨论对其中部分决策做了升级与修正，
> 修正结论见 `docs/schema.md` 的「讨论结论」一节与仓库 README。

用途：交给 Claude Code 作为项目起点。以下是已经讨论清楚的决策，以及待定事项。

## 一、产品定位

做一个网页文字游戏的创作工作台 + 游玩平台。用户提供 idea，平台解决实现问题（不用会 GitHub、不用会部署）。

不是"中国版 Lovable"。Lovable 那类通用 builder 国内已经很挤（百度秒哒、秒悟、Trae 等）。定位收窄为：文字游戏（叙事类 + 数值模拟类）的一站式创作与发布平台。

差异点：

- AI 生成降低创作成本（对比橙光要付费买素材）
- 现代技术栈、作品可导出（橙光锁死作者，是它最大的怨气来源）
- 文字品类无美术需求 → 与主流 AI 游戏平台（都在卷 Spine 动画、美术资产）不在同一战场

已有资产：作者自己做的 `val manager`（类足球经理的网页文字游戏，已部署在 Railway）。这是 template zero，也是抽象通用 schema 的源材料。

## 二、核心架构决策（已定，可直接实现）

**1. 多租户单应用，不做 per-user 部署**

- 一个游戏 = 数据库里的一条数据（JSON），不是一次部署
- 所有游戏跑在同一个 app 内，路由区分：`/g/:id`
- 用户点"发布" = 把记录标记为公开，不触发任何 build / deploy
- 不需要给用户任何 GitHub / Railway 账号，这个需求本身不存在

**2. 编辑器与播放器同源**

- 玩家看到的页面 = 作者预览时的渲染器，换一份数据、去掉编辑控件
- 一套引擎两种模式，工作量约等于一份

**3. 免登录游玩**

- `/g/:id` 不需要注册即可玩，进度先存 localStorage
- 玩到一半想存档，再引导注册（此时已有沉没成本）
- 这一条决定传播能否跑通，不可妥协

**4. 路由结构**

```
/            首页（游戏列表 —— 冷启动期先不开，见下）
/g/:id       游玩，免登录
/edit/:id    编辑，需登录
/u/:name     作者主页
```

**5. 静态优先，动态留接口**

- 第一版全静态：AI 只在创作阶段介入，产出一个不依赖 AI 就能跑的游戏 → 边际成本为零
- 架构上只需保证"事件"是数据驱动的：静态版从预写事件池抽，未来动态版让 AI 现场生成一条塞进同一个池子，渲染与结算逻辑复用
- 不要为了未来的动态功能现在改设计

## 三、技术要点（容易埋雷的地方）

**1. 用户自定义公式 —— 绝对不要用 eval**

用户需要定义结算逻辑（比赛胜负、属性成长等）。方案二选一：

- 自定义受限表达式语法：只允许四则运算、比较、变量引用
- 或塞进 Web Worker + 超时限制

直接跑用户写的 JS = 死循环、XSS、数据越权。

**2. AI 输出的结构化与校验（工作量最容易被低估）**

让模型生成游戏配置时，一定会出现：JSON 格式错、引用不存在的变量、结局条件永远触发不了。需要：

- JSON Schema 校验层
- 校验失败自动重试
- 语义错误（悬空引用、不可达结局）要能报给用户

这一层的工作量比"调 API"大 5 倍。

**3. AI 配额系统**

第一天就做，按次数或 token 记账，防薅。

**4. 上下文管理（未来动态路线用）**

如果做实时生成：全历史进 prompt → 成本随回合数平方增长。必须用滚动摘要（压缩的状态描述 + 最近 N 回合原文）压回线性。

## 四、第一版范围

做：

- 游戏 schema 定义（下一步的第一件事，见第六节）
- 渲染引擎（跑一份 JSON 就能玩）
- 编辑器（能改这份 JSON）
- AI 辅助生成（自然语言 → schema，带校验）
- 分享链接（技术含量约等于零，但是留存命门）
- 把 val manager 迁成第一个模板，验证 schema 通用性

先不做：

- 首页公开列表 —— 冷启动期只有十几个半成品，空列表在告诉用户"这里没人"。等有 30–50 个能玩完的游戏再开
- 排行、评论、关注 —— 有量了再说
- 实时 AI 生成剧情 —— 先测成本再决定
- 备案、牌照、支付 —— 见下

## 五、合规（当前阶段策略：全部延后）

当前阶段（十几个用户内测，不大规模传播），风险近似为零，只需两个动作：

1. 域名与服务器放境外（Vercel / Railway 自带域名即可），不碰境内服务器 → 备案是绑服务器的，不触发
2. 一分钱不收 → 不构成经营行为

未来一旦要放量或收费，这些会成为硬墙（记录备查，现在不做）：

- ICP 备案（境内服务器必须，个人可办）
- ICP 许可证（增值电信业务经营许可证）—— 只要收费就需要，必须公司主体
- 网络文化经营许可证 —— UGC 游戏平台通常要
- 内容审核 —— UGC + AI 生成叠加，法律硬要求，需接第三方（阿里云内容安全 / 腾讯天御 / 网易易盾）
- 实名认证 + 防沉迷

注意：游戏跑在自己域名下，内容责任在平台方。所以内测期保持邀请制，人少时可人工过一遍每个游戏。

已知小问题：微信内打开 Railway 这类域名容易被拦，内测期让用户复制到浏览器打开即可，不值得为此折腾。

## 六、下一步：先定 schema

这是整个系统的地基。编辑器 UI、渲染器、AI 输出格式三者都要照着它长，定错了三处一起返工。

方法：从 val manager 倒推，不要凭空设计。需要梳理清楚的：

- 实体与属性怎么存（球员 / 能力值）
- 时间单位是什么（一场比赛 / 一周 / 一赛季）
- 结算公式怎么表达（比赛胜负怎么算）
- 随机事件池的结构
- 玩家可做的决策（转会、训练、战术）如何定义
- 成长 / 衰退曲线怎么配

目标是抽象出一套能同时表达"足球经理"和"修仙宗门经理""乐队经理""餐厅经营"的通用骨架 —— 这类 management sim 本质是同一套 schema 换名词和公式，换皮空间很大。

叙事类（分支树、变量、结局条件）是否与 sim 类共用一套 schema，还是两套模板，待定。建议先只做 sim 类跑通，因为已有实例。

## 七、待验证 / 未决问题

1. 动态生成的真实成本 —— 拿 val manager 做实验：一次赛季循环的 prompt 实际 token 数 × 平均回合数，用国内模型（DeepSeek / 豆包 / Qwen）价格算。一个下午能出结论
2. 中间态方案值得先试：主线与结算全静态，只让 AI 生成不影响逻辑的 flavor text（解说词、球员抱怨、小事件描述），生成失败 fallback 到预写文本。零风险，性价比可能最高
3. 叙事类与 sim 类是否共用 schema
4. val manager 能否靠内容本身传播 —— 推到 NGA / 虎扑 / B 站足球区，看能否拿到几千玩家。跑通了同时验证三件事：文字 sim 有人玩、内容可传播、有人会问"这怎么做的"（这批人就是前 200 个创作者）

## 八、背景参考

- 橙光（66RPG，2012 起）：文字游戏 UGC 平台的国内先例，2018 年注册用户 5500 万+、签约作者 3400+、作品 130 万部。证明了非技术用户愿意做文字游戏，量级是千万
- 橙光衰落的四个原因 = 本项目的切入口：作者要付费买素材、内容品相老旧、作品不能导出（作者被锁死，最招恨）、品类同质化严重
- 橙光冷启动路径：前 200–300 个创作者来自已有的 66RPG 论坛，之后靠一款爆款（《清宫计》）带来大量新作者 → 说明"先有社区/爆款，后有平台"，推广不是靠投放
- 相邻竞品：闪艺（文字游戏）、SOON / 灵珠（AI 游戏生成，但主攻美术资产与休闲小游戏）、Twine（海外，要替代的现状）
